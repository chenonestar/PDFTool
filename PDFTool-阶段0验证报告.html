1. 结论

"点段落 → 改字 → 保存"的方案可行，可以进入阶段 1。 在生成的 4 类电子版样本（混合字体通知、表格、双栏、加密文件）上，改字、加长、缩短、改数字都能在原位置正确重排；表格框线和底纹不受影响；撤销 / 重做、覆盖保存、自动备份、重新打开后文字一致，全部自动化检查通过。
还没有在 Windows 真机上运行过 开发环境是 Linux：Windows 版 exe 已交叉编译成功（20.4MB），但 WebView2、Windows 系统字体（宋体、微软雅黑等）、原生对话框这几项只能在 Windows 上确认。另外生成的样本模拟不了 Word / WPS 真实导出的内部结构，需要用你日常的文件再试一次。见第 8 节。

2. 做了什么

  • 项目骨架：Wails v2 + Svelte 5 + TypeScript；WebView2 用户数据目录指向 data/webview/；启动时检查程序目录可写；WebView2 按"系统 → webview2/ 目录 → 中文提示"的顺序查找；构建参数 -webview2 error。
  • Go 后端：/api/file（读文件）、/api/save（POST 回写：首次覆盖前备份、先写临时文件再替换）、/api/fonts / /api/font（系统字体枚举与读取，支持 TTC 子字体）；备份按天数清理。
  • PDF 引擎（Web Worker）：页面渲染、段落识别、段落编辑五步流程、撤销 / 重做（MuPDF journal）、保存（在副本上字体子集化 + 垃圾回收）。
  • 界面：打开 / 保存 / 另存为 / 撤销 / 重做 / 缩放；"编辑文字"模式下鼠标悬停显示段落框，点击弹出原位编辑框（Ctrl+Enter 确定、Esc 取消）；密码输入框；状态栏显示耗时和警告（超出原区域、缺字、字体替换）。页面按需渲染。
  • 测试：样本生成脚本、断行单元测试（9 项）、引擎端到端检查（编辑 → 撤销 → 重做 → 保存 → 重新打开）、Playwright 浏览器端到端测试、Go 后端测试；GitHub Actions 在 Windows 上构建 exe。

3. 验证清单结果

验证项（需求文档 7 节阶段 0）结果说明
系统字体嵌入，TTC 按索引加载通过从 TTC 中按索引加载子字体并嵌入，保存时子集化（一个 10MB 的 TTC 子集化后约 45KB）。发现：MuPDF 不能对 CFF 轮廓（OpenType/PostScript）字体做子集化，会把整个字体（20MB+）嵌进去。Windows 自带的宋体、黑体、微软雅黑、楷体、仿宋、等线都是 TrueType，不受影响；对用户自装的思源 / Noto 等 CFF 字体，改为自动换用相近的 TrueType 字体，并在状态栏提示。
redaction 只删文字，不删表格线和图片通过表格样本改了 3 处，页面上 22 个线条 / 色块全部保留，底纹不受影响。
中文断行和避头尾通过句号、逗号、右括号等不出现在行首（悬挂在上一行行尾）；左括号、左引号不出现在行尾；西文单词不拆开；两端对齐、居中、右对齐、首行缩进都按原段落处理。
mupdf.js 是否暴露 journal 接口通过enableJournal / beginOperation / undo / redo 都可用；每次段落修改是一步，多步撤销 / 重做正常。
AssetServer 传输大文件（读取和 POST 回写）部分通过同一套 Handler 在开发服务器上验证通过（600 页文件打开 110ms）。Wails 源码确认 Windows 下 AssetServer 支持请求体，但还需真机确认。
mupdf.js 是否支持 docx 输出不支持mupdf.js 的 WASM 构建没有包含 DOCX / ODT 输出（报错"DOCX/ODT writer not enabled"）。按需求文档的对策，PDF 转 Word 延后，到阶段 7 再找方案。

6. 过程中发现并解决的问题

问题处理
MuPDF 把行距较大的段落拆成"每行一个文本块"自己实现段落合并：按字号、行距、左边界、上一行是否排满来判断
MuPDF 会在中文和数字之间自动补空格（"2026 年"）提取时关闭（inhibit-spaces）
Word / WPS / LibreOffice 用"填充 + 描边"模拟粗体，字体信息里看不出来遍历页面时记录描边文字的位置，识别为粗体；写回时同样用描边模拟
写回的描边线宽在下一次修改时被 MuPDF 的内容过滤丢掉，粗体变得过粗线宽改用 ExtGState 设置，过滤后能保留
Go 的 x/image/sfnt 解析部分 TTC 报错自己写了只读 name / OS/2 表的极简解析器
Worker 里 WASM 加载完成前发出的消息会丢失界面线程等 Worker 报告 ready 后再发送
字体子集化会改动正在编辑的文档、破坏撤销记录保存时在副本上做子集化

7. 已知限制

  • 中英文之间的间距：Word / LibreOffice 排版时会在中文和数字 / 英文之间加约 1/4 字宽的间距，重排后的段落没有这个间距，看起来稍紧。可在阶段 2 补上。
  • 文字变多时不会推开下方内容：排版行数超过原段落时会与下方内容重叠（状态栏有提示）。表格单元格同理。
  • 原字体不在本机时会换用相近的系统字体（宋体类 / 黑体类 / 楷体类），外观会有差异。
  • 单行段落的对齐判断是推测的（例如表单里的短标签可能被误判为右对齐）；表单控件区域还没算进可用宽度的限制。
  • 改过的段落在内容顺序上会排到页面末尾：显示没有影响，但复制整页文字时顺序会变。阶段 2 可以改为写回原位置。
  • 编辑框里的预览字体是浏览器字体近似，确定后页面上显示的才是实际效果。
  • 阶段 0 只有单文档，多标签、缩略图等在阶段 1 实现；关闭窗口时的未保存提醒也在阶段 1 接入 Wails 的关闭事件。

8. 需要你来做的

  1. 从 GitHub Actions 下载 Windows 版：仓库的 Actions 页面 → 最新一次 build → 产物 PDFTool-windows-amd64（如果 Actions 没有运行，也可以按 README 在 Windows 上自己构建）。
  2. 把 PDFTool.exe 放到一个可写目录（如 D:\Tools\PDFTool\）双击运行，确认：能启动、data/ 自动创建、%APPDATA% 下没有新建 PDFTool 相关目录。
  3. 用 2–3 个日常真会改的 Word / WPS 导出文件试一下改字，告诉我哪里效果不好（最好附上文件或截图）。
