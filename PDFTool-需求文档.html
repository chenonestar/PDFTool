1. 项目概述

PDFTool 是一款自己用的 Windows 桌面 PDF 编辑工具，不需要安装，也不联网。目标是在日常使用中替代福昕、WPS 等商业 PDF 编辑器，覆盖下面几类需求：

  • 阅读和整理 PDF：合并、拆分、重排页面等；
  • 直接修改 PDF 里原有的文字和图片，尽量接近原生编辑的体验（这是本项目的重点）；
  • 批注、签名、填写和制作表单；
  • 扫描件 OCR 识别；
  • PDF 和图片、文本、Word、Office 文档之间的转换。

界面采用"编辑器 + 工具箱"结合的形式：主界面是类似 Acrobat、福昕的文档编辑器，另有一个工具箱面板，用来批量处理合并、压缩、加水印、OCR、格式转换等任务。

2. 运行环境与发布形态

项目要求
操作系统Windows 10 / 11，64 位
运行依赖优先使用系统自带的 Microsoft Edge WebView2 Runtime（Win10 一般已随 Edge 安装，Win11 内置）；系统没有时，使用程序目录下 webview2/ 中的固定版本运行时（默认不带，需要时自行放入）。查找顺序见下方"WebView2 运行时"
安装方式绿色免安装：解压即用，不写注册表，不往 AppData 写数据，整个文件夹拷走即可使用。实现要点见下方"便携性约束"
存放位置程序目录必须可写（如 D:\Tools\PDFTool\），不要放在 C:\Program Files\ 等受保护目录下
网络完全离线运行，不联网
体积目标主程序约 20–30MB（含 MuPDF WASM），OCR 模型另计约 15–20MB

2.1 发布目录结构

PDFTool/
├── PDFTool.exe              # 主程序（Wails 打包，前端资源内嵌）
├── webview2/                # 可选，默认不带：WebView2 固定版本运行时，仅系统缺少 WebView2 时使用
├── ocr/                     # OCR 模型与运行库
│   ├── onnxruntime.dll      # 仅 Go 端推理方案需要，见 3.1
│   ├── det.onnx             # 文字检测模型
│   ├── rec.onnx             # 文字识别模型
│   └── keys.txt             # 字典
└── data/                    # 程序首次运行时自动创建
    ├── settings.json        # 设置
    ├── recent.json          # 最近打开的文件
    ├── signatures/          # 签名库
    ├── stamps/              # 自定义图章
    ├── backup/              # 覆盖保存前的原文件备份
    └── webview/             # WebView2 用户数据（缓存等），见下方说明
便携性约束（实现时必须处理）
  • WebView2 用户数据目录：Wails v2 默认把 WebView2 的用户数据放在 %APPDATA%\PDFTool.exe\ 下，会违反"不写 AppData"。必须通过 options.Windows.WebviewUserDataPath 指定为程序目录下的 data/webview/。
  • 文件关联：设为 PDF 默认打开程序需要写注册表，程序本身不做文件关联注册。由用户在 Windows"打开方式 → 始终使用此应用"中手动设置，程序只负责处理命令行参数传入的文件路径。
  • 目录不可写：启动时检测程序目录是否可写；不可写（例如放在 Program Files 下）时弹窗提示用户把程序移到其他目录，不回退到 AppData。
WebView2 运行时（默认不带，按需放入） 程序主要在自己的电脑上使用，Win10 / 11 基本都已装有 WebView2，因此默认发布版不带运行时，保持程序小巧。启动时按以下顺序查找：
  1. 系统 WebView2：已安装就直接使用（常规情况）；
  2. 程序目录下的 webview2/：系统没有时，检查该文件夹中是否有微软提供的 WebView2 固定版本（Fixed Version）运行时，有就通过 Wails 的 options.Windows.WebviewBrowserPath 指定使用；
  3. 都没有：弹出中文提示（说明可以安装 WebView2 Runtime，或把固定版本运行时解压到 webview2/），然后退出。
查找由程序自己在调用 wails.Run 之前完成。构建时指定 -webview2 error，避免 Wails 默认的"联网下载安装 WebView2"行为，符合离线要求。
固定版本运行时体积较大（下载包约 150MB，解压后更大，具体以实测为准），且不会自动更新；本程序离线运行、只加载自身页面，安全影响很小。

3. 技术方案

3.1 技术选型

部分选型说明
程序外壳Wails v2Go 后端 + TypeScript 前端，打包为单个 exe
前端Vite + TypeScript + SvelteSvelte 5（已确定）
PDF 引擎MuPDF（mupdf.js，WASM）在前端的 Web Worker 中运行，负责渲染、结构化文字提取、内容编辑、批注、表单、页面操作、保存。放在 Worker 里，处理大文件时界面不卡。撤销 / 重做使用 MuPDF 自带的 journal（操作日志）机制
中文字体系统字体由 Go 后端从 C:\Windows\Fonts（及用户字体目录）读取宋体、黑体、微软雅黑、楷体等，不打包大字体；保存时只嵌入用到的字（字体子集化），控制文件体积。注意宋体（simsun.ttc）、微软雅黑（msyh.ttc）等是 TTC 字体集合，加载时要指定子字体索引。MuPDF 只能对 TrueType 轮廓的字体做子集化，CFF 轮廓（OpenType/PostScript，如思源 / Noto）会整个嵌入，因此写入时优先 TrueType 字体
Go 后端Go 标准库 + Wails 绑定文件读写、覆盖保存与备份、系统字体枚举与读取、OCR 推理（如采用 Go 端方案）、调用 Office/WPS 转换、打印、命令行参数（支持双击 PDF 用本程序打开）、设置存储
文件传输Wails AssetServer 自定义 HandlerWails 绑定调用会把 []byte 转成 base64 JSON 传递，大文件又慢又占内存。PDF、字体等二进制数据一律走 AssetServer 的自定义 Handler：前端用 fetch 直接取得 ArrayBuffer，保存时以 POST 回传。绑定调用只传路径、参数等小数据
OCRPaddleOCR（PP-OCR）模型 + ONNX Runtime中文识别准确率明显好于 Tesseract。推理位置两种方案待阶段 6 前实测决定：
① Go 端：速度快；但常见的 Go 绑定（如 onnxruntime_go）依赖 cgo，需要 MinGW 工具链，构建变复杂（Wails v2 在 Windows 上本身不需要 cgo）；
② 前端：用 onnxruntime-web（WASM）在 Worker 中推理，免 cgo，发布更简单，不需要 onnxruntime.dll，但速度较慢
Office 转 PDFCOM 自动化调用本机已安装的 Microsoft Office 或 WPS 导出 PDF；本机没装时该功能不可用
打印Worker 渲染 + Go 调用系统打印不使用 WebView2 打印 canvas（效果和可控性较差）。由 Worker 按打印机分辨率（如 300 / 600 DPI）把页面渲染成位图，交给 Go 后端通过 Windows 打印接口（打印对话框 + GDI）输出。阶段 1 验证打印质量与速度

3.3 正文编辑实现要点

mupdf.js 能提供结构化文字提取、redaction（真正删除内容）、添加字体和字体子集化，但没有现成的"文本框排版"能力，段落编辑的排版部分需要自己实现。一次段落修改的处理流程：

  1. 提取：用结构化文字提取拿到段落的行、字、字体、字号、颜色、坐标，推算行距、字距、对齐方式。
  2. 删除原文字：在段落区域加 redaction 并应用，参数设为只删文字：不画黑框、图片不处理、线条不处理。否则表格框线、底纹等会被一起删掉。
  3. 排版（自己实现）：按原段落宽度断行。中文按字断行并处理避头尾（句号、逗号等不出现在行首，左括号、左引号等不出现在行尾）；西文按单词断行；支持左对齐、两端对齐、居中；匹配原行距和字距。
  4. 写回：生成新的文本内容流写回页面；中文使用 Identity-H 编码的 CID 字体；原字体缺字时换用系统字体（见 4.3"缺字回退"）。
  5. 保存：保存时做垃圾回收和字体子集化。

整个修改包在一次 journal 操作里，一步撤销即可恢复原样。阶段 0 需要把这五步都跑通。

7. 开发计划

先验证风险最大的正文编辑，再搭底座，然后按使用价值依次推进。每个阶段结束都有能用的成果。

阶段 0

技术验证

搭好 Wails 项目骨架（WebView2 用户数据目录指向 data/webview/；实现 WebView2 运行时查找顺序，并实测一次使用 webview2/ 固定版本运行时启动）；让 mupdf.js 在 WebView2 的 Worker 里跑起来；完成页面渲染和"点段落 → 改字 → 保存"的最简原型（跑通 3.3 的五个步骤）。同时验证以下几点：

  • 系统字体嵌入，包括 TTC 字体集合按索引加载；
  • redaction 只删文字、不删表格线和图片；
  • 中文断行和避头尾；
  • mupdf.js 是否暴露 journal 接口（撤销 / 重做）；
  • AssetServer 传输大文件（读取和 POST 回写）；
  • 顺手确认 mupdf.js 是否支持 docx 输出。

验收：用上述样本测试，确认文字编辑效果可以接受。效果不达标则在此阶段调整方案。

8. 风险与对策

风险影响对策
正文编辑效果达不到预期核心功能体验差阶段 0 先用真实文件验证；不达标时降级为"擦除原文字 + 原位重写"的方式
原 PDF 字体是子集，缺字新输入的字显示不出来自动回退到相近的系统中文字体；保存时嵌入新字体子集
mupdf.js 在 WebView2 中处理大文件的性能和内存大文件卡顿在 Worker 中运行；按需渲染；阶段 0 顺带测试大文件
OCR 模型体积与识别精度程序变大或识别不准采用 PP-OCR 轻量模型；阶段 6 前做选型验证
PDF 转 Word 效果有限复杂版式还原差定为 P2，"尽力还原"，不作为核心功能
电脑缺少 WebView2程序无法启动启动时按"系统 → webview2/ 目录"顺序查找；都没有时中文提示，用户可把固定版本运行时放进 webview2/ 后直接使用
WebView2 默认往 AppData 写用户数据违反绿色免安装要求设置 WebviewUserDataPath 指向 data/webview/；阶段 0 检查 AppData 下没有新建目录
Wails 绑定传 []byte 走 base64 JSON大文件打开、保存慢，内存翻倍二进制数据统一走 AssetServer 自定义 Handler；阶段 0 用 100MB 级文件测试
删除原文字时误删表格线、底纹改字后版面被破坏redaction 参数设为只删文字；阶段 0 用带表格的文件验证
段落排版需自己实现工作量大，中文断行效果不理想阶段 0 先做最简版（单一字体、左对齐 + 避头尾），阶段 2 再补两端对齐、混合字体等
mupdf.js 未暴露所需接口（journal、docx 输出等）撤销 / 重做或 PDF 转 Word 要另想办法阶段 0 逐项确认；journal 不可用时改为保存文档快照做撤销；docx 不可用时 PDF 转 Word 延后
OCR 放在 Go 端需要 cgo构建需要 MinGW，交叉编译和打包更复杂阶段 6 前对比 Go 端和前端（onnxruntime-web）两种方案后再定
系统字体为 CFF 轮廓（思源、Noto 等）无法子集化，整个字体嵌入，文件增大几十 MB写入和缺字回退只用 TrueType 字体；原字体是 CFF 时换用相近的 TrueType 字体并提示（阶段 0 已实现）
打印质量和速度位图打印文件大、速度慢按打印机实际 DPI 渲染、逐页提交；阶段 1 实测
